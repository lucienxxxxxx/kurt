# 代码风格规范

> 渐进式披露文档。先读第 1 节掌握硬规则；只有在改对应包或场景时，再读后续细节。

## 1. 必读硬规则

1. 先读索引再动代码：根 `PROGRESS.md` 用来对齐项目状态，相关包的 `PROJECT_INDEX.md` 用来定位文件，相关包的 `CLAUDE.md` 用来确认硬性约束。
2. 保持依赖方向：前端包可以依赖 `kurt-agent`，`kurt-agent` 不能依赖任何前端、协议、UI 或桌面层。
3. `kurt-agent/src/engine/` 零 I/O：不能访问文件、网络、控制台、进程、环境变量、时间或工作目录。副作用只能放在工具、沙盒、会话、搜索、MCP、worktree 或外层编排里。
4. 新能力优先加壳：新增 LLM、工具、记忆、沙盒、MCP、skill、子 agent 时，优先实现接口或外层 composition shell，不改 engine 承重代码。
5. 对象以能力边界命名：一个类或模块代表一个可替换能力，例如 `ModelProvider`、`Tool`、`SandboxProvider`、`PermissionProvider`、`AskProvider`、`SessionStore`、`ToolHub`。
6. 跨模块只吃公共接口：包外消费走 `src/lib.ts`，目录外消费优先走该目录 `index.ts` barrel，避免深层路径耦合。
7. 测试锁不变式：事件顺序、tool_call/tool_result 配对、路径 confinement、权限审批、并发行为、会话原子写等必须有测试；修 bug 先补复现或回归测试。
8. 代码保持 TypeScript 严格模式友好：显式类型边界、`unknown` 入参先校验、避免隐式 `any`、尊重 `noUncheckedIndexedAccess`。
9. Import 使用显式 `.ts` 扩展，优先 type-only import，私有状态使用 `#field`。
10. 注释解释契约和非显然取舍，不复述语句。承重模块顶部保留短契约注释，普通函数只在读者会误解时加注释。

## 2. kurt-agent 分层规范

### 2.1 Engine

`packages/kurt-agent/src/engine/` 是核心协议和事件循环，只允许纯内存逻辑。

- 可以放：`runLoop`、核心事件/消息类型、注入接口、队列、纯 compaction seam。
- 不可以放：具体 provider 适配、文件读写、权限弹窗、shell、MCP 连接、session 持久化、UI shape。
- 判断标准：换一个 LLM 厂商、换沙盒实现、换前端协议时，engine 不应该需要修改。

### 2.2 Provider

`src/providers/` 负责把厂商 wire format 消化成 engine 的标准 `ModelStreamEvent`。

- 厂商差异必须在 provider 内结束：SSE 格式、tool call 参数拼接、thinking/reasoning 字段、token usage、错误消息。
- API key、base URL、模型选择由编排层传入，不在 provider 内读取环境。
- 新厂商先实现 `ModelProvider`，再在外层运行时选择；除非核心事件契约缺失，不改 engine。

### 2.3 Tool

`src/tools/` 是 engine 允许触达副作用的主要入口。

- 每个工具实现 `Tool`，输入为 `unknown`，先校验再执行。
- 文件路径必须经 `resolveWithin` 或等价 confinement；模型提供的路径不能直接拼接使用。
- 长输出必须截断，长任务必须可中断，子进程必须有 idle/hard timeout。
- 风险操作必须走 `PermissionProvider` 或 `request_access` 类工具，不把 UI 审批逻辑塞进工具。
- 工具错误返回 `ToolResult { isError: true }`，除非是不可恢复的程序错误；让 engine 保持“工具失败但 loop 不崩”的不变式。

### 2.4 Agent / ToolHub / 组合层

`src/agent/` 是对象化组合层，不是第二个 engine。

- `Agent` 只绑定 `{model, system, tools, compaction}` 并委托 `runLoop`。
- `ToolHub` 是已构造工具的注册表，用于按模式挑选工具。
- `AgentProfile` / `AgentRuntime` 承载 persona、memory context、工具子集和策略组合；继续把 planning policy、sub-agent routing 做成 profile/policy seam，避免把状态和策略塞回 `runLoop`。

### 2.5 Session / Memory

`src/session/`、`src/memory/` 和 `MemoryTool` 属于编排层持久化能力。

- 会话存储、锁、原子写可以 I/O，但不得让 engine 知道存储位置。
- 记忆模块保持“编排层预载 + 工具写入 + store 后端”的模型，避免模型可控路径。
- 默认后端是 `MarkdownMemoryStore`；后续 RAG 后端实现 `MemoryStore.search` 和检索注入策略，不改 engine。

### 2.6 MCP / Skills

- MCP 是远程工具提供方：包装成 `Tool` 后进入 `ToolHub`。
- Skill 是渐进披露上下文：系统提示只注入 name/description，正文通过 `skill` 工具按需加载。
- 不要混淆三者：Tool 是可执行能力，MCP 是工具来源，Skill 是指导数据。

## 3. TypeScript 细节

- 文件命名使用短横线小写：`openai-compat.ts`、`request-access.ts`。
- 类型和类使用 PascalCase；函数、变量、方法使用 camelCase；常量使用 SCREAMING_SNAKE_CASE 仅限真正常量。
- 公共导出要有稳定名字；临时 helper 留在文件内，不急着导出。
- 外部输入保持 `unknown`，用类型检查或小型 parser 收窄。
- 返回结构优先用明确 interface/type，不用松散对象穿透多层。
- 并发逻辑要显式说明顺序语义：事件实时顺序、历史记录顺序、错误配对规则分别是什么。
- 使用 Bun 原生能力优先于 Node/npm 等价物；但如果已有模块使用 Node 标准库且更适合该场景，可以沿用现有模式。

## 4. 注释和文档风格

- 承重文件顶部写“这个模块是什么、边界是什么、保证什么不变式”。
- 函数内部注释只解释非显然原因，例如 provider 兼容需求、沙盒限制、并发顺序、数据安全。
- 不写空泛注释，例如“设置变量”“执行函数”。
- 文档里的状态要和 `PROGRESS.md`、包级 `PROJECT_INDEX.md` 保持一致；结构性变更后更新索引。
- 对 agent 可读文档使用渐进披露：摘要、硬规则、导航、细节、示例依次展开，避免把长背景塞到第一屏。

## 5. 测试规范

- 测试放在被测代码旁边，命名 `*.test.ts`。
- engine 测试优先锁定事件契约和历史结构，不依赖真实 I/O。
- provider 测试用注入的 `fetchImpl` 或本地 fixture，不打真实外网。
- 工具和 sandbox 测试允许使用临时目录，但必须可重复、可清理、输出有上限。
- 会话/状态写入测试覆盖并发安全、原子写、损坏文件容错和锁释放。
- 文档-only 变更至少做链接/拼写/路径 sanity check；源码变更按包运行 `bun run typecheck && bun test`。

## 6. 新能力放置决策表

| 需求 | 首选位置 | 不该放在哪里 |
| --- | --- | --- |
| 新 LLM 厂商 | `src/providers/<vendor>.ts` + 外层 runtime 选择 | `src/engine/loop.ts` |
| 新本地工具 | `src/tools/<name>.ts` + `src/tools/index.ts` | provider、engine |
| 新沙盒策略 | `src/sandbox/<name>.ts` | ShellTool 内硬编码 |
| 新审批规则 | `src/permission/classify.ts` 或前端 allowlist | engine |
| 新记忆后端 | `src/memory/` 的 `MemoryStore` 实现 + 工具/编排调用 | engine 消息循环 |
| 记忆 RAG 检索 | `MemoryStore.search` 后端 + prompt 注入策略 | `runLoop` / provider |
| 新前端协议 | sibling package 或 bridge 层 | kurt-agent engine |
| 新子 agent | `SubAgentTool` / agent 组合层 | 改写 runLoop 主循环 |

## 7. Review 清单

- 这次改动是否扩大了 `kurt-agent` 对前端、协议或运行时依赖的认知？
- 是否有副作用进入 `src/engine/`？
- 是否新增了可替换能力却没有接口边界？
- 模型可控输入是否经过校验和 confinement？
- 长任务是否可中断、限时、限输出？
- 并发结果是否有确定的历史顺序和测试？
- 公共 API 是否只通过 barrel 暴露？
- 对应 `PROJECT_INDEX.md` / `PROGRESS.md` 是否需要更新？
